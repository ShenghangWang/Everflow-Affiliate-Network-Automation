**Important Architectural Strengths:**

* **Strict Rule-vs.-Model Authority & Financial Safety (`architecture.md §§3, 4, 6`):** Models have zero direct tool/credential access, zero financial arithmetic responsibility, and cannot self-authorize dispatches or modify commercial terms. Binding `(target, recipient, action, content_version, terms_version, policy_version, expiry)` with three-stage revalidation (creation, claim, pre-transport) prevents silent approval drift.
* **Clear Separation of Business Stage vs. Execution State (`architecture.md §§3–4`):** Separating lead/account lifecycle stages from outbox transport states (`scheduled`, `authorized`, `executing`, `succeeded`, `cancelled`, `failed`, `unknown_outcome`) and refusing to blindly resend on transport timeouts avoids the most common reliability failure in automated outreach systems.

**Credible Simpler Alternative (vs. Preference):**

* **Single-Process Synchronous SQLite + Scheduled CLI Tick (Alternative to Background Lease Worker for the Day 2–3 Local Prototype):** For a strictly single-user local loopback demo (`127.0.0.1`) using mock transport and an injected fake clock, running a separate background polling worker with lease tokens (`architecture.md §1`, `ADR01`) adds lifecycle and test-synchronization complexity. A simpler, equally auditable local prototype alternative is to keep the exact same `inbox`/`outbox` tables and state transitions (`scheduled` → `authorized` → `executing` → `succeeded`/`unknown_outcome`), but trigger worker ticks deterministically via an explicit API endpoint (`POST /api/worker/tick` or UI "Advance Clock & Run Due Actions" button) inside the same FastAPI process.
* *Defect vs. Preference Distinction:* Using a background worker with leases (`ADR01`) is an architectural **preference** (and a good forward-looking choice for production parity), **not a defect**—provided `F01`, `F05`, and `F07` are addressed.
